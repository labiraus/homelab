## Storage follow-up evidence (2026-10-11)

The original archive tool sorted by timestamp/version ID and refused equal timestamps. Boto3 exposes versions and delete markers in separate arrays; that representation alone cannot establish their relative order within a tied timestamp. Schema-2 archives now retain and verify mixed XML listing evidence, preserving opaque IDs and complete pagination across two different page sizes. AWS documents the listing and marker contract in [ListObjectVersions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html). See the [ordering procedure and refusal boundaries](../StorageVersionMigration.md); actual installed source inventory/restore remains required.

The [SeaweedFS smoke test](../../scripts/seaweedfs-smoke.py) now includes real lost initiation/part/completion replies and an explicit `--large-migration` case: a 5 GiB + 17 byte import/re-export with full hashes, headers, tags and bounded client memory. Storage CI requires the large case. Part sizing respects [S3 multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html); protocol bounds are not evidence of SeaweedFS capacity. The orchestrator's version-map schema-1 resolver remains compatible. Acceptance/publication evidence is tracked in increment 24, independently of the still-open ordering item.

Provider source audit: [SeaweedFS 4.48 version listing](https://github.com/seaweedfs/seaweedfs/blob/4.48/weed/s3api/s3api_object_versioning.go) uses interleaved XML and key/version pagination, but has bounded-collection ordering limits for old-format directories. Its [comparator](https://github.com/seaweedfs/seaweedfs/blob/4.48/weed/s3api/s3api_version_id.go) places `null` last regardless of latest status. The checker validates non-null wire chronology and positions null only by a distinct timestamp; tied null versions remain refused. Tests cover inconsistent legacy-style pages/latest state, but agreeing listings cannot prove a defective provider exposed all stored history. MinIO source automation (`ansible/roles/minio_server/defaults/main.yml`) has a floating binary URL; installed source version, inventory completeness and restored historical reads remain LAN gates.

## Reference coverage follow-up evidence (2026-10-11)

The source audit identifies `rag.documents.version_marker` and all three `rag.document_change_audits` version-marker columns as explicit S3 references. Preserve their bucket/key identity; audit rows can survive a deleted inventory row (`document_pk ON DELETE SET NULL`), so joining only current documents loses history. `assistant.file_proposals.orchestrator_response` and `assistant.tool_calls.arguments/result` can retain returned version markers and historical audit records. Saved messages/citations and arbitrary metadata also need bounded inspection and explicit unresolved-reference reporting.

Current Go/Node lifecycle constructors do **not** emit an S3 version marker; their `processingVersion`, like citation/chunk processing versions, is an integer derived-index generation. Never reinterpret it as an S3 version ID. Inspect legacy/extended lifecycle JSON rather than assuming today's shape covers production history. Missing bucket/key context, blank markers, unversioned current inventory, delete markers and source/alias/destination collisions remain explicit coverage outcomes; literal `null` version IDs can be mapped. The [snapshot exporter and offline checker](../StorageReferenceCoverage.md) now implement this preparation, including reviewed missing-context evidence without history rewrites. Production coverage remains unobserved.
