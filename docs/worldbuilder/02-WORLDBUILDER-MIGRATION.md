canonical-policy and ephemeral-chat contracts. See [current implementation,

The dated checkpoints below are retained as historical evidence.


## Approach

Incremental pivot inside the existing homelab monorepo. The original target assumed separate `engine` and `infra` repositories, but this checkout already contains PostgreSQL, Go services and a Node HTTP processor. **Inspect before changing**; illustrative paths are not deployment instructions. Preserve working clusters, hardware, toolchains, networking, authentication and Flux release conventions. Avoid broad renaming or unrelated refactoring. Separate source-code readiness from cluster-validated completion. Build milestones in order, using feature flags/adapters to avoid half-migrated flows. The [acceptance matrix](ACCEPTANCE-MATRIX.md) is the current assessment; milestone gates below define requirements rather than asserting current failures.

## Required initial repository audit (M0)

1. Inventory all service directories and their interfaces, read `README*`, `AGENTS.md`, project planning documents, architecture decision records, OpenAPI specs, deployments, CI pipelines and any autogenerated docs.
2. Inventory Cassandra tables/queries/users, migration data risks, OpenSearch pipelines/indexes, existing NATS streams/consumers, AI workflow code, Envoy integration and UI features.
3. Locate Helm chart values, Flux HelmReleases/Kustomizations, Terraform modules, image build/release/versioning, secrets injection, Cilium/Istio routes and existing database backups.
4. Produce a concise current-vs-target gap table with **confirmed files and symbols**; distinguish facts from assumptions. Identify which existing document functions can be adapted and which should be retired.
5. Start an execution log: `docs/worldbuilder/IMPLEMENTATION-STATUS.md` with milestone, changed paths, checks run and **blocked cluster checks**; keep a decision log and remediation log.

## Milestones and gates

### M1 — PostgreSQL foundation
- Add database connection support, migration tooling, typed DB access, test database and transactional helper patterns in Go.
- Add PostgreSQL deployment configuration or managed-service configuration consistent with infra conventions; secrets, persistent volume, backup and observability specs.
- Keep Cassandra operational until consumer migration is verified; write explicit Cassandra data inventory/export plan. Do not discard records by assumption.
- Gate: migration up/down compatibility tests; code compiles and tests pass; manifests render. Record actual cluster connectivity, role isolation and storage/restore evidence separately from disposable tests; consult the current acceptance matrix before repeating migration work.

### M2 — Canon domain
- Implement world/member, entity type/schema, entity, fact, relationship, event, timeline and rule service/repositories plus API contracts.
- Add real-time vs fictional-time abstraction and timeline scoping. Keep graph queries behind interfaces; start with relational queries/recursive CTEs.
- Implement current projections + immutable historical revision representation; prove historical read/reconstruction in tests.
- Gate: world isolation, relationship integrity, chronology and version-read tests; wiki API usable without LLM.

### M3 — Change sets and governance
- Implement draft operations, deterministic validation, approval roles, review policies, immutable audit and publication transaction.
- Lock/check world current revision, detect stale proposals, apply all operations or none, persist outbox event, idempotency handling.
- Gate: conflict, concurrency, compensating rollback, bypass prevention and atomic failure tests.

### M4 — Wiki and editor
- Follow the [AI-first UI specification](05-AI-FIRST-UI.md): conversation is the primary workspace, with existing wiki/editor/review/story tools integrated around it. Track UI-0–UI-6 and API gaps in [UI implementation](UI-IMPLEMENTATION.md); do not replace working domain contracts with mockups.
- Add world dashboard, structured entity editor, relationship/history navigation, searchable wiki, change diff/review workflow and history.
- Gate: a user can create a world and progress data from draft through human-approved published wiki entry without AI.

### M5 — Grounded AI and indexing
- Replace document-centric assumptions with authorised tool APIs for canon, relationships, timeline, rules and references.
- Implement `canon_query`, `canon_proposal`, `consistency_check` workflows; require typed output validation and explicit uncertainty.
- Reconfigure OpenSearch indexing from authoritative events/projections, including world/timeline/revision and visibility metadata. Keep original source documents in object storage or approved current storage.
- Use existing Envoy AI Gateway and provider configuration; verify embeddings path and inference feature support rather than assume compatibility.
- Gate: test dataset with source-linked factual queries, missing-fact response, cross-world isolation, adversarial prompt injection and index rebuild.

### M6 — Interactive story engine
- Implement story definition, sessions, pinned canon revision, provisional typed facts/state transitions, turns, concurrency and idempotency.
- Add LangGraph story-turn and scenario generation workflow, bounded memory / persisted summaries, persistent narration and cost attribution.
- Use orchestrator jobs for truly long-running generations; recover incomplete jobs safely.
- Gate: session survives restart, concurrent actions cannot corrupt state, generated output alone never mutates canonical facts.

### M7 — Story outcomes and visualisation
- Extract canonical outcome **proposals** from story sessions; reconcile against current revision and route through M3 validation/approval.
- Build optional relationship graph and chronology views, without adding another authoritative database.
- Gate: end-to-end complete story -> review -> publish -> wiki/search; conflicts produce reviewable findings.

### M8 — Cutover and cleanup
- Inventory residual Cassandra uses, identify data to migrate or explicitly archive, run schema/data consistency checks, verify backups and restore.
- Rebuild OpenSearch from authoritative sources; compare counts, citations and indexes; run end-to-end security, rollback and multi-user checks.
- Remove Cassandra code/manifests/credentials **only after** verification and an explicit operator-approved decommission checkpoint.
- Gate: end-to-end acceptance, recovery drills, observability dashboards, runbooks, cluster validated; no silent deletion.

## Documentation reconciliation policy — required

The old Evolve project plan, architecture and operational docs may contradict the pivot. Do not simply append new prose while leaving stale authoritative claims in place.

1. **Discover and classify** every relevant Markdown and generated source (readmes, `docs/**`, AGENTS files, architecture diagrams, ADRs, API specifications, helm comments and runbooks). Build `docs/worldbuilder/DOCS-AUDIT.md` with current path, owner/purpose, status (`retain`, `update`, `supersede`, `archive`, `delete-candidate`), reason and replacement link.
2. **Update** active entry points and indexes (`README`, docs index, onboarding, platform overview) to describe Worldbuilder, current implementation status, and links to the four new docs. Preserve accurate infra/security guidance.
3. **Revise** stale application architecture/data/RAG docs to reflect PostgreSQL authority, domain facts, OpenSearch-as-index, changesets, story separation, service responsibilities and currently implemented state. Remove outdated statements from active docs, not only add banners.
4. **Retain historical decisions** as dated ADRs with `Superseded by ...` notices; do not rewrite history or erase useful rationale. Archived docs should be visibly marked historical, moved only after checking inbound relative links.
5. **Delete only duplicates or demonstrably obsolete generated/stale material** once all incoming links and dependencies are fixed, and record deletions in the docs audit. Prefer archival for valuable historic context. Never delete AGENTS instructions without preserving legitimate operational guidance.
6. **Update generated specs from their source** (OpenAPI, diagrams, schema docs, Helm READMEs) and regenerate outputs through existing tooling. Never manually edit a generated file if a generator is present.
7. Search for leftover `Cassandra`, `document-first`, `assistant` service, prior product name and old route names. Do not naively mass-replace legitimate historical, file path, technology or infrastructure references. Distinguish current vs target status in every operational document.
8. Verify relative links, Markdown syntax, service diagram consistency, command accuracy, deployment naming, ADR cross-references and no contradictory current-state claims. Log unresolved questions instead of inventing answers.
9. Update docs **in each implementation milestone**, not only at the end: plan, decisions, current state, troubleshooting, API/schema docs and appropriate changelogs.

## Developer / Codex self-documentation rules

Maintain `IMPLEMENTATION-STATUS.md`, `DECISIONS.md`, `TROUBLESHOOTING.md` and `DOCS-AUDIT.md` under `docs/worldbuilder/`. Record meaningful design decisions (context, alternatives, reason, tradeoffs), diagnosed failure and proven fix, and actual test results with command/context. No fake passing checks, no invented deployed state. If existing repository conventions specify other paths, integrate rather than duplicate these logs.

## Cutover safeguards

Never mix a new authoritative PostgreSQL write path with Cassandra authoritative writes indefinitely. Choose and document a migration window, backups, repeatable export/transform/import, checksum/count and logical integrity verification, fallback routing, and the source of truth at each step. Backwards-incompatible service and DB deployment must be coordinated. Explicitly gate irreversible migrations, PVC/PV changes, old database scale-down, secret deletion and resource removal.
